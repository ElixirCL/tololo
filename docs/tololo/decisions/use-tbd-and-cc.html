Use Trunk Based Development and Conventional Commits

  • Status: accepted

  • Date: 2025-01-13

Context

In order to standarize contributions and commit messages we will use Trunk Based Development and Conventional Commits.

TBD is a source-control branching model, where developers collaborate on code in a single branch called ‘main’, resist any pressure to create other long-lived development branches by employing documented techniques. They therefore avoid merge hell, do not break the build, and live happily ever after.

The Conventional Commits specification is a lightweight convention on top of commit messages. It provides an easy set of rules for creating an explicit commit history; which makes it easier to write automated tools on top of. This convention dovetails with SemVer, by describing the features, fixes, and breaking changes made in commit messages.

The commit message should be structured as follows:

<type>[(optional scope)][optional !]: <description>

[optional body]

[optional footer(s)]

The commit categories will be (based on @commitlint/config-conventional):

  • chore: Another change that do not fits any other category.

  • refactor: Modify or delete existing code.

  • feat: Implements a new feature.

  • docs: Modify or creates documentation.

  • fix: Fix a bug.

  • test: Adds or improves tests.

All casing in the category and scope must be lowercase.

All merge commits must reference the pull request number in the squash message. Once merged the sender branch will be deleted.

Examples

feat: allow provided config object to extend other configs in #232

feat!: send an email to the customer when a product is shipped in #412

feat(api)!: send an email to the customer when a product is shipped in #42

chore!: drop support for Node 6 in #24

Decision

We will use Trunk Based Development, as a branch strategy and Conventional Commits as a commit message standarization.

Consequences

  • Conventional commits will only be required inside the Squash Commit merge option inside the Pull Request. The developer can add as many commits and any format it needs. But the final Squash Commit message must follow Conventional Commits and reference the Pull Request number and a summary of the changes inside its body.

  • Pull Request must have at least 1 approval of another developer before merge them inside main.

  • Pull Request must always be updated with the latest main version and do not have merge conflicts.

  • Pull Request must pass the test suite before merge to main.

  • main branch must always be runnable. Pull Request must not break main.

  • Each commit on main will trigger a new build action that will release a "nightly version" that will update the semver.
