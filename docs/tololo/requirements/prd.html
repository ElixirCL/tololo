Product Requirements Document

The product requirements document (PRD) is a living document that can help you align a variety of stakeholders a set the project up for success. The main objective is to develop a compelling plan that team members and stake holders are excited about and support.

The intended audience for this document are developers that want to understand the main objectives for this project.

Context

It is needed an ecommerce solution for small businesses, specially restaurants with delivery. That do not require monthly payments or additional expenses (outside server and payment gateway costs). A solution that is Libre (AGPLv3), Free, made with modern tools, well documented and can be used by small stores and restaurants.

State of the Art

eCommerce has experienced positive growth in Chile over the last decade due to Chile’s rapid and continuing technological infrastructure development, the launch of 5G service in December 2021, and the popularity of eCommerce since the beginning of the COVID-19 pandemic. According to Statista, 64.8 percent of Chileans bought online during 2022, and this percent will continue to grow each year, reaching 69.4 percent by 2027, driven by a high internet penetration of 91 percent in 2022. The Santiago Chamber of Commerce has a Manual of Best Practices for eCommerce. This code serves as a guide to ethical behavior for eCommerce providers and operators for the benefit of consumers and users.

Platforms such as Justo Ecommerce and PedidosYa are available for restaurants and take away delivery. These are closed source Software as a Service and Markeplaces that require monthly payments or a percentage of the each sold item.

For the API and architectural decisions, we considered LunarPHP and MedusaJS, both open-source headless ecommerce solutions.

Solution

The solution will be oriented as a libre/free alternative to Justo Ecommerce. Will focus on the use case "Small Restaurant with Take Away". Other inspirations can be pizza deliveries such as Melt Pizza, Papa Johns, and Underpizza.

Our plan is to make an API as simple as LunarPHP’s, while leveraging the events system of MedusaJS with Kafka, to allow extending the system with an existing one. This event-driven architecture would enable seamless system extensions and integrations with other tools, such as inventory management. Kafka ensures reliable event processing and allows the system to scale as demand grows, while also providing durability for critical data like order status updates or inventory changes.

The solution will also allow live tracking of deliveries, by connecting an app to an endpoint exposed by the backend. The endpoint will handle periodic location updates from the delivery app, providing customers access to real-time delivery tracking via a public URL.

Live tracking allows customers to monitor their orders in real-time, improving trust and reducing inquiries about delivery status.

Dependencies

  • Frontend:

    • The solution is purely headless, so a separate frontend must be provided for customers to interact with the backend API.

  • Cloud Hosting Solution:

    • A cloud hosting platform (e.g., AWS, Google Cloud, DigitalOcean) that supports running a Docker image for deployment.

  • PostgreSQL Database:

    • A PostgreSQL database instance is required for storing the application’s data (e.g., orders, products, user data).

  • Kafka (Optional):

    • A Kafka instance is needed if event-driven functionality is required, allowing for the handling of asynchronous events (e.g., order processing, inventory updates).

  • Prometheus & Grafana (Optional):

    • Prometheus and Grafana instances are necessary for system monitoring and reporting, enabling performance metrics and real-time analytics dashboards.

Functional Requirements

  • The customer can adquire food items using an API or frontend app.

  • The customer can modify the ingredients and other available customization options.

  • The customer can request delivery or pick items on site.

  • If the delivery option is selected, a realtime map can be viewed inside a public URL.

  • The business owner can have a "backoffice" with product and prices.

  • The business owner can see sales reports and other relevant statistics (Based on Grafana and Prometheus).

  • The solution must integrate with at least 1 chilean payment option (besides direct deposit). (Flow or Mercadopago).

  • The solution must send events relevant to inventory, sales, delivery and order status to Kafka, if configured.

Non Functional Requirements

  • The system must be similar to Justo in UX and features.

  • The system should include clear installation instructions and require minimal configuration to get started.

  • The system should handle dependencies seamlessly, avoiding manual intervention for typical use cases.

Acceptance Criteria

  • Product Browsing

    • The customer can access the full list of products through the exposed endpoints.

    • The product data includes relevant details (name, description, price, and customization options).

    • Search functionality returns relevant products based on customer queries.

  • Product Customization

    • The customer can modify product options (e.g., choose pizza toppings, product size, color, etc.).

    • The system reflects changes immediately in the total price.

  • Shopping Cart

    • The customer can add items to the cart through the exposed endpoints.

    • The cart displays updated totals, including taxes and delivery fees.

    • The customer can remove items from the cart or change quantities.

  • Checkout Process

    • The customer can complete the checkout process.

    • The system accepts at least one payment method (e.g., Flow, MercadoPago, etc.).

    • The system confirms payment success/failure, and sends confirmations and status updates as notifications.

  • Delivery Tracking

    • The system provides live tracking of deliveries through a public URL.

    • The customer can view the location of their delivery in real-time (via a map).

    • Location events can be received through the exposed endpoint.

  • Backoffice

    • The business owner can manage product listings and inventory (add, update, delete).

    • The business owner can set product prices and customize available options.

    • The business owner can view sales reports and statistics (via Grafana/Prometheus integration).

  • Headless Compatibility

    • The system must be fully headless, and a frontend can be integrated without requiring code changes to the backend.

    • The solution should support multiple frontend apps (e.g., mobile apps, PWAs).

  • Event-driven Architecture

    • Events should be published and consumed successfully.

    • The Kafka event system should function properly and allow easy extensions or integrations (e.g., for inventory management).
